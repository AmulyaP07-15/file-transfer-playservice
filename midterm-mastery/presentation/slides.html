The Service
How the service works
A client asks for a file over HTTP. The gateway fetches it from the backend over UDP in 64 byte chunks, up to about 4 MB. It answers 200, 404, 503 busy, or 504 no answer.

Experiment 3
Load and autoscaling on AWS
  • Vary  Locust load 10, 50, 200, 0 users, 5 min each
  • Fixed  10 KB file, 0 percent loss, deploy defaults
14,364 requests 63% failed, all 503 p95 7.1 s gateway 2 → 4 tasks backend stays 2 ECS CPU ~3%
The gateway scales on request count and grows 2 to 4. The backend scales on CPU, but a UDP server is not CPU bound, so CPU sits near 3 percent and it never scales. Even at 4 gateway tasks, max inflight 4 means most of 200 users are shed with 503. CPU is the wrong scaling signal for this backend.

What this reveals
Three ways it breaks
1
It cannot tolerate loss on large files. The chunked UDP protocol with a fixed retry budget stops converging once more than a few chunks go missing.
2
It scales on the wrong signal. The backend scales on CPU but is never CPU bound, so it never scales where the real work is.
3
It sheds load early. The gateway allows only four transfers in flight per task, so it returns 503 well before it is truly saturated. And the AWS network behaves like a lossy link even with no configured loss.

What I would test next
Limitations
  • 20 downloads per level shows the cliffs but does not put error bars on the edges

What I would test next
  • Finer loss levels around 1 to 2 percent, with more repeats
