The Service
How the service works
A client asks for a file over HTTP. The gateway fetches it from the backend over UDP in 64 byte chunks, up to about 4 MB. Replies are 200 ok, 404 not found, 503 busy (no free transfer slot on the gateway), or 504 (the backend never finished the transfer).

Why these three experiments. Loss, size, and load probe protocol reliability, protocol scalability, and deployment scalability. I hold the retries (5 tries, 5 rounds) and max inflight (4) fixed and vary one thing at a time. On AWS the gateway and backend autoscale on different signals, which Experiment 3 shows really matters.

Experiment 3AWS
Load and autoscaling on AWS
  • Vary  Locust load 10, 50, 200, 0 users, 5 min each
  • Fixed  10 KB file, 0 percent loss, deploy defaults
14,364 requests 63% failed, all 503 p95 7.1 s gateway 2 → 4 tasks backend stays 2 ECS CPU ~3%
The gateway scales on request count and grows 2 to 4. The backend scales on CPU, but a UDP server is not CPU bound, so CPU sits near 3 percent and it never scales. Even at 4 gateway tasks, max inflight 4 means most of 200 users are shed with 503. CPU is the wrong scaling signal for this backend.

AWS MetricsCloudWatch
What CloudWatch showed
I pulled the AWS side metrics from CloudWatch to confirm, from the infrastructure view, what the service did during the load test.
  • the ALB saw about 2,100 requests per minute at peak, about 1,700 of them 5xx (the 503 shedding)
  • target response time rose from about 2.3 s to about 6 s under load
  • ECS CPU stayed near 3 percent for both services, far below the 60 percent target
This is why the backend never scaled. Its scale out alarm watches CPU, and CPU never came close to 60 percent.

What this reveals
Three ways it breaks
1
It cannot tolerate loss on large files. The chunked UDP protocol with a fixed retry budget stops converging once more than a few chunks go missing.
2
It scales on the wrong signal. The backend scales on CPU but is never CPU bound, so it never scales where the real work is.
3
It sheds load early. The gateway allows only four transfers in flight per task, so it returns 503 well before it is truly saturated. And the AWS network behaves like a lossy link even with no configured loss.

Limitations and next steps
What I would test next
Limitations
  • 20 downloads per level shows the cliffs but does not put error bars on the edges
  • Experiment 3 effectively ended near 15 minutes, and I did not wait for the slow scale in
What I would test next
  • Finer loss levels around 1 to 2 percent, with more repeats
  • Raise the gateway max inflight and run the load test again
  • Change the backend scaling signal from CPU to active transfers or NLB flow count
